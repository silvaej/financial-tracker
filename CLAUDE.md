# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commit messages

Brief, imperative, prefixed with a type tag: `(feat) <description>`, `(fix) <description>`, `(chore) <description>`, etc. No `Co-Authored-By` trailer.

## UI changes

For a new or redesigned UI surface, design first: produce a visual mockup (e.g. a rendered Artifact using the app's existing ledger palette/fonts) and get sign-off on the direction before writing the real implementation. Small tweaks to existing UI (copy, spacing, a single component) don't need this.

## Stack

FastAPI backend rendering server-side HTML via Jinja2, progressively enhanced with HTMX (no client-side JS framework, no JSON API). PostgreSQL via SQLAlchemy 2.0 (typed `Mapped`/`mapped_column` models), Alembic for migrations. Poetry for Python dependency management. Tailwind CSS (standalone CLI, no Node/npm) for styling. Docker Compose for local dev (`db`, `web`, `tailwind` services).

## Commands

Start everything via Docker Compose (installs deps, builds CSS, runs migrations, seeds sample data if the DB is empty, starts the server):

```
docker compose up --build
```

Then, in a second terminal, run Compose's file-sync watcher so edits to `app/`/`alembic/` actually reach the containers and trigger Tailwind's rebuild / uvicorn's `--reload`:

```
docker compose watch
```

Both are needed for local dev on Windows/Mac: `web` and `tailwind` intentionally have **no bind mount** (see below), so without `watch` running, file edits never reach the containers at all. `docker compose watch` also handles rebuilding the image automatically when `pyproject.toml`/`poetry.lock` change.

App is served at http://localhost:8000. Postgres is exposed on localhost:5432 (credentials in `.env` / `.env.example`).

Add/update a Python dependency (regenerates `poetry.lock`, which the Dockerfile installs from — rebuild the image after):

```
poetry add <package>
docker compose up --build
```

Create a migration after changing `app/models.py`:

```
docker compose run --rm web alembic revision --autogenerate -m "describe change"
docker compose run --rm web alembic upgrade head
```

(`alembic upgrade head` also runs automatically on `web` container start.)

Running without Docker (e.g. against local Postgres or SQLite for a quick check): `poetry install`, set `DATABASE_URL`, run `poetry run uvicorn app.main:app --reload`. Swap in a `sqlite:///./dev.db` URL to avoid needing Postgres at all — SQLAlchemy/Alembic don't care which dialect as long as `psycopg2` isn't imported at that path. You'll also need the `tailwindcss` standalone binary on PATH (or run it via `docker compose run --rm tailwind` against the same mounted volume) to regenerate `app/static/css/style.css`.

### Lint, type-check, test

```
poetry run ruff check .            # lint (import order, bugbear, pyupgrade, etc.)
poetry run ruff format .           # format
poetry run mypy app tests          # type-check (strict-ish: disallow_untyped_defs)
poetry run djlint app/templates --profile jinja --reformat   # format Jinja/HTML
poetry run djlint app/templates --profile jinja --check      # check only
poetry run pytest                  # test suite
```

Or via Docker, e.g. `docker compose run --rm web poetry run pytest`.

`tests/conftest.py` overrides the `get_db` FastAPI dependency with an in-memory SQLite session (StaticPool, so all connections in a test share the same DB) — tests never touch Postgres and don't need `psycopg2` importable. `Base.metadata.create_all`/`drop_all` run around every test via an autouse fixture, so each test starts from a clean schema. When adding a route, add a test that posts/gets through the `client` fixture and asserts on the rendered HTML fragment (there's no JSON to assert on — see Architecture below).

mypy is configured with `disallow_untyped_defs`, so every function (including router handlers and pytest fixtures) needs a full signature — annotate `-> HTMLResponse` (or whatever) even though FastAPI doesn't require it at runtime.

## Domain

Modeled after a personal "ledger" budgeting workflow (income arrives on recurring payout dates, gets routed between accounts, and pays bills), not a generic transaction list:

- **Channel** — a bank account, e-wallet, or credit card (`name`, `color`). User-managed (add/rename/recolor/delete), not hardcoded — this is what lets the app work for anyone's actual accounts rather than one specific bank setup.
- **PayoutPeriod** — a recurring pay date (e.g. "15th", "30th") with its own `income_amount` and a `receiving_channel` — the channel that payout's income lands in first.
- **Expense** — a recurring bill: `name`, `amount`, tied to one `PayoutPeriod` and one `Channel` (which channel it's paid from).
- **Transfer** — an explicit, user-entered money move between two channels *for a specific payout period* (`from_channel`, `to_channel`, `amount`). This is how money routes onward from a period's receiving channel to wherever it actually needs to end up (e.g. a savings account, a second wallet used to pay credit cards).
- **`crud.channel_balances(db, payout_period_id)`** (`app/crud.py`) is the core calculation: for a given payout period, each channel's net = its `income_amount` (only if it's that period's `receiving_channel`) + incoming transfers − outgoing transfers − expenses tagged to it. This is the generalized replacement for a fixed cash-flow diagram — since channels/routing are user-defined rather than hardcoded, there's no single fixed diagram shape; instead every payout period gets a computed balance table from whatever transfers/expenses exist. Note this means "remainder" amounts (e.g. "whatever's left after other transfers") are **not** auto-derived — every transfer amount is explicit and user-edited, same as any other field.
- **Goal, CreditLine, Asset** — shipped sections (`app/routers/{goals,credit,assets}.py`, full page + partial templates each), not placeholders. A `Goal` (`target`, `months`, an optional `channel`) is funded incrementally via `GoalContribution` rows (`goal`, `channel`, `payout_period`, `amount`) — the same "explicit, per-payout-period, user-entered" shape as `Transfer` above, tracked separately from `Goal.allocated`. `CreditLine` (`limit`/`used`) and `Asset` (`amount`) are simpler standalone entities, each optionally tagged to a `Channel`.
- **User** — every other table has a nullable `user_id` FK to `users.id`; the app is multi-tenant, each user's channels/periods/expenses/etc. are fully isolated from every other user's. Login is Google/GitHub OAuth only (no password — see Architecture below). No *unrestricted* public registration — a brand-new email signing in via OAuth still needs a valid, unexpired, not-yet-exhausted `SignupKey` (`app/models.py`), which the operator generates via `manage_users.py create-key` (see below); an OAuth sign-in for an email that **already has a `User` row** (created via `manage_users.py create`, or a prior signup) auto-links with no key needed. `app/manage_users.py`'s `create` subcommand remains the only way to create an account *without* going through a key.

## Architecture

- **Request flow**: `GET /` renders Overview (`app/routers/overview.py`, `app/templates/overview.html`) — home, not Expenses. Overview, Expenses, Goals, Credit, Assets, Cash Flow, and Export (CSV downloads, no page of its own) are all real registered routers; `app/main.py`'s `PLACEHOLDER_SECTIONS` dict is now empty, so the `/{section}` catch-all route is effectively just a 404 handler rather than an actual placeholder for anything — add a real route+template ahead of it if a genuinely new top-level section shows up. There is no JSON API and no client-side state; the DOM is the state.
- **Fragment contract — whole-page re-render**: unlike a typical HTMX app that swaps small fragments, every mutating route across `app/routers/channels.py`, `payout_periods.py`, `expenses.py`, and `transfers.py` re-renders and returns the *entire* `partials/expenses_page.html` fragment (via a shared `_render_page()` helper in each router) targeting `#expenses-page` with `outerHTML`. This is deliberate: channels and payout periods feed `<select>` dropdowns and computed balances all over the page, so a full-page-content re-render keeps everything consistent without juggling many separate swap targets. The page is small enough that this has no real performance cost. `crud.expenses_page_data(db)` is the single function that assembles all the context (channels, payout periods, expenses, and a `payout_data` list of `{period, transfers, balances}` per period) that both `GET /` and every mutating route render from — keep using it rather than re-deriving context ad hoc in a new route. Goals/Credit/Assets follow the same `_render_page()` + single `crud.*_page_data()` pattern independently, each against its own partial (`partials/goals_page.html`, etc.) — not the Expenses page's context.
- **DB access**: `app/database.py` provides `get_db()` (a FastAPI dependency yielding a `Session`); routers depend on it and delegate all queries to `app/crud.py` — routers should stay thin (parse form input via `app/schemas.py` Pydantic models, call `crud`, render a template).
- **Optional FK form fields**: HTML `<select>` "no selection" options submit as an empty string, not an absent field — `int | None = Form(None)` on a route parameter does NOT accept `""` and will 422. See `payout_periods.py`'s `_parse_channel_id()` helper (`str = Form("")` in the signature, converted to `int | None` manually) for the pattern to copy wherever an optional FK is selectable in a form.
- **Models vs. migrations**: `app/models.py` is the source of truth for schema. `alembic/versions/0001_initial.py` was originally rewritten in place (not layered with a new revision) back when this project had no deployed data yet; staging/prod now have real data, so every schema change since (the OAuth migration included) is a new additive revision instead — don't edit `0001_initial.py` or any other already-shipped migration.
- **Styling**: `app/static/css/input.css` defines the ledger palette/fonts via Tailwind v4's `@theme` (e.g. `--color-ink`, `--color-accent`, `--font-serif` for Fraunces, `--font-mono` for IBM Plex Mono) plus a `@layer components` block of reusable classes (`.card`, `.section`, `.pill`, `.led` table, `.field`, `.badge`, etc.) mirroring the original mockup's own hand-written CSS class names — use these existing classes in new templates rather than inlining new utility combinations or `style="..."` attributes (djlint's `H021` rule flags inline styles). `app/static/css/style.css` is the compiled, gitignored output; don't hand-edit it. `app/templates/macros.html` has a `channel_badge(channel, size)` macro (colored initials badge) — import and reuse it (`{% import "macros.html" as macros %}`) anywhere a channel is displayed rather than re-deriving initials.
- **Dependencies**: `pyproject.toml`/`poetry.lock` are the source of truth. The Dockerfile runs `poetry install` with `POETRY_VIRTUALENVS_CREATE=false`, installing straight into the image's system Python rather than a venv inside the container. `requirements.txt` at the repo root exists only for Vercel's Python builder (see CI/Deployment below) — it's generated, not hand-edited: `poetry export -f requirements.txt --output requirements.txt --without-hashes` (needs `poetry-plugin-export`, installed alongside Poetry itself with `pip install poetry poetry-plugin-export` — it's a Poetry CLI plugin, not a project dependency, so it doesn't belong in `pyproject.toml`). Regenerate it any time `poetry.lock` changes; CI fails if it's out of sync.
- **Local dev file sync**: `web`/`tailwind` in `docker-compose.yml` deliberately have no `.:/code` bind mount — on Windows (and often Mac) hosts, in-container watchers (Tailwind's `--watch`, uvicorn's `--reload`) don't reliably see filesystem-event notifications through a bind mount, so edits silently fail to trigger a rebuild/reload even though the file content itself would be up to date. `develop.watch` (`docker compose watch`) works around this by pushing changes into the container through the Docker engine instead, which the in-container watchers *do* see. Keep source changes under the watched paths (`app/`, `alembic/`) — anything outside those needs an image rebuild (`pyproject.toml`/`poetry.lock` already trigger one automatically via a `rebuild` watch action). Notably, **`tests/` is not a watched path** — editing a test file and immediately `docker compose exec web poetry run pytest` runs the *stale* copy baked into the image with no warning that anything's out of sync. Either rebuild, or push the one file directly with `docker compose cp tests/test_x.py web:/code/tests/test_x.py` before running it (same fix as the `static_css` gotcha below, different root cause: this one's a missing watch path, not a shadowing volume). This also means one-off commands like `alembic revision --autogenerate` need an extra bind mount for `alembic/versions` to actually reach the host (`docker compose run --rm -v "$(pwd)/alembic/versions:/code/alembic/versions" web alembic revision --autogenerate -m "..."`), and the image must be rebuilt first if `app/models.py` changed since the last build — otherwise autogenerate compares against a stale schema and produces an empty migration.
- **`app/static/css` is a blind spot for `docker compose watch`**: both `web` and `tailwind` mount the named volume `static_css:/code/app/static/css`, which shadows that subpath — `develop.watch`'s sync (scoped to `./app` → `/code/app`) cannot write into it, so edits to `input.css` silently never reach either running container, no matter how long `docker compose watch` runs. There's no error or log line about this; the symptom is just "my CSS change isn't showing up" indefinitely. If a CSS-only change isn't taking effect, verify staleness with `docker compose exec web grep -c '<a snippet from your edit>' app/static/css/input.css` (`0` means it hasn't synced) or `docker compose exec web ls -la app/static/css` (compare the `input.css` mtime to when you actually edited it). Force it through with `docker compose cp app/static/css/input.css web:/code/app/static/css/input.css` followed by `docker compose exec web tailwindcss -i app/static/css/input.css -o app/static/css/style.css` (the volume is shared, so this updates it for `tailwind` too) — or just restart the stack (`docker compose down && docker compose up --build`, which recreates the volume from the image) if you'd rather not think about it.
- **Auth**: session-cookie based (Starlette's `SessionMiddleware`, added in `app/main.py`, signed with `settings.secret_key` — set a real `SECRET_KEY` env var in any real deployment; the in-code default is dev-only). Login itself is Google/GitHub OAuth, not a password — `app/oauth.py` registers both providers via `authlib.integrations.starlette_client.OAuth` and exposes `fetch_identity(provider, client, token)` (returns `(provider_user_id, verified_email)`, `None` email if the provider has no verified address on file). `app/routers/oauth.py`'s `GET /auth/{provider}/start` stashes an optional `invite_key`/`keep_signed_in` in the session before redirecting to the provider; `GET /auth/{provider}/callback` exchanges the code, then either logs into an existing `OAuthIdentity` (`app/models.py`), auto-links a matching-email `User` with no key needed, or — for a genuinely new email — validates the stashed invite key and creates the account. `app/auth.py`'s `start_session`/`get_current_user` (a FastAPI dependency reading `request.session["user_id"]`) are unchanged by this — every route that touches user data still depends on `get_current_user` and passes `current_user.id` into `crud.py`. Unauthenticated access raises `NotAuthenticated`, caught by an `app.exception_handler` in `main.py` that returns `HX-Redirect: /login` for htmx (`HX-Request`) requests and a plain 303 otherwise — needed because htmx won't follow a normal redirect response for a boosted/AJAX request, it'll just swap the redirect target's HTML into the page.
- **OAuth account linking**: `OAuthIdentity` (`provider`, `provider_user_id`, `email`, `user_id`) links one or more provider identities to a `User` — linking is by verified email, so signing in with a different provider under the same email attaches a second identity to the existing account rather than creating a duplicate. `crud.get_oauth_identity()`/`create_oauth_identity()` are the relevant `crud.py` functions. Local dev needs real OAuth app credentials (`GOOGLE_CLIENT_ID`/`SECRET`, `GITHUB_CLIENT_ID`/`SECRET` in `.env`, redirect URIs `http://localhost:8000/auth/<provider>/callback`) — there's no password fallback, so without these `/login`'s provider buttons don't work.
- **Per-user data isolation**: every `crud.py` function takes a `user_id` and filters by it; `crud._owned()`/`_require_owned()` are the shared helpers — `_owned` does an ownership-scoped lookup (returns `None` for both "doesn't exist" and "belongs to someone else", deliberately indistinguishable), `_require_owned` is used to validate every FK a form submits (e.g. a channel's `funding_source_channel_id`, an expense's `channel_id`/`payout_period_id`) actually belongs to the acting user before a create/update proceeds, raising `crud.OwnershipError` (routers turn this into a 404) if not. Follow this pattern for any new entity/route rather than a bare `db.get(Model, id)`.
- **`login.html`/`signup.html` don't extend `base.html`** — `base.html` unconditionally renders the full authenticated app shell (rail nav, htmx-boosted), so both auth pages are standalone templates with their own `<html>`/`<head>`, sharing only the compiled stylesheet and a `partials/auth_visual.html` include (the decorative ledger-preview panel) between them.
- **`app/manage_users.py`** — CLI for account management (`create`, `assign-orphans`, `create-key`), run via `poetry run python -m app.manage_users <subcommand> <email>` against whichever `DATABASE_URL` is in the environment (same invocation style as `app/seed.py`). No web UI for account creation — deliberately, since registration is still gated. `create <email>` makes a passwordless `User` row that's claimed the first time someone signs in via OAuth with that email (no key needed, since the row already exists — see Domain above). `create-key` (no email argument; takes `--max-uses`/`--expires-days`) is the only way to mint a `SignupKey` for a brand-new email's first OAuth signup. `assign-orphans` backfills any orphaned rows (`user_id IS NULL` — pre-auth data, or `app/seed.py`'s sample data, see Staging below) to a chosen user.
- **Session lifetime**: `app/auth.py`'s `get_current_user()` enforces its own idle (`SESSION_IDLE_TIMEOUT_SECONDS`, 30 min) and absolute (`SESSION_ABSOLUTE_TIMEOUT_SECONDS`, 7 days) timeouts independently of the session cookie's own lifetime — a login with "Keep me signed in" checked (`start_session(..., keep_signed_in=True)`) skips the idle check entirely and uses a longer absolute cap (`KEEP_SIGNED_IN_ABSOLUTE_TIMEOUT_SECONDS`, 30 days) instead. `SessionMiddleware`'s `max_age` (`app/main.py`) is set to the longer of the two (`SESSION_COOKIE_MAX_AGE_SECONDS`) since Starlette only supports one fixed cookie lifetime per app — the shorter default is enforced by the app's own checks, not the cookie's expiry.

## Branching

`main` (prod) and `dev` (staging) are both protected: no direct pushes, everything goes through a PR. `main` only accepts PRs from `dev`; `dev` only accepts PRs from feature branches (never directly from `main`). The `enforce-branch-source` job in `.github/workflows/ci.yml` checks `github.event.pull_request.base.ref`/`head.ref` and fails any PR that breaks these rules; it's set as a required status check on both branches' GitHub branch protection settings (0 required approving reviews — single-developer repo — but PRs are still mandatory).

## CI / Deployment

- **CI**: `.github/workflows/ci.yml` runs on every push/PR — `ruff check`, `ruff format --check`, `mypy app tests`, `djlint --check`, `pytest`, and a `requirements.txt` drift check (`poetry export` output must match the committed file). `migrate-prod` (pushes to `main`) and `migrate-staging` (pushes to `dev`) each run `alembic upgrade head` against `secrets.PROD_DATABASE_URL` / `secrets.STAGING_DATABASE_URL` respectively.
- **Dependabot auto-fix**: `dependabot.yml` targets the `pip` ecosystem at `/`, which means Dependabot bumps two different things depending on whether a package is a *direct* dependency: real ones declared in `pyproject.toml` (e.g. `ruff`) get bumped properly through `poetry.lock`, but anything only *transitive* (not declared anywhere in `pyproject.toml`, e.g. `mako`, `websockets`, `pydantic-core`) gets bumped by Dependabot editing the committed `requirements.txt` directly, since it treats that file as its own independent pip manifest — `poetry.lock` is never touched for those. **Do not "fix" a failing Dependabot PR by just running `poetry export` over `requirements.txt`** — for a transitive-only bump that blindly regenerates the file from `poetry.lock` (which was never updated) and silently reverts the bump back to the old version while looking like a clean, passing fix. `.github/workflows/dependabot-autofix.yml` (triggered on `push` to `dependabot/**` branches, actor-gated to `dependabot[bot]` to avoid retriggering itself) does this correctly: it runs `poetry update <package>` first (parsed from the PR title via `scripts/classify_version_bump.py`) so the bump is a real resolution, not just a file regeneration — if Poetry's resolver can't actually reach the proposed version (blocked by another package's pin, as happens with `pydantic-core` being locked to whatever exact version `pydantic` requires), the job leaves a comment and skips auto-merge rather than merging a misleading version bump. It also re-runs `ruff check --fix`/`ruff format` for tooling bumps (e.g. ruff itself) that introduce new lint/format violations, then enables auto-merge for patch/minor bumps only (major bumps always need manual review) once real CI passes. The fix-commit is pushed using a `DEPENDABOT_PAT` repo secret (a real user credential), not the default `GITHUB_TOKEN` — GitHub's recursion guard means a `GITHUB_TOKEN`-authored push doesn't retrigger the PR's own required checks, which would leave the PR stuck showing pending/stale checks forever even after the fix landed.
- **Deploy**: Vercel, connected via its GitHub git integration (set up once in the Vercel dashboard — not something this repo's code controls) — production deploys from `main`, preview deploys from `dev` only. `api/index.py` re-exports `app.main:app` as the ASGI entrypoint; it sits at a location (`api/index.py`) Vercel's zero-config FastAPI detection recognizes automatically, so every path — including `/static/*`, served by the app's own `StaticFiles` mount rather than Vercel's static hosting — routes to it without any `rewrites` entry. **Do not add a catch-all `rewrites` rule** (e.g. `{ "source": "/(.*)", "destination": "/api/index" }`) — that was a pre-zero-config workaround, and Vercel changed same-app rewrites to route using the literal rewritten destination path rather than the original request path, so every request would hit FastAPI's router as `GET /api/index` and 404 (this broke staging for a while before being caught — see git history around vercel.json if it recurs). `vercel.json`'s `buildCommand` re-runs the same standalone-`tailwindcss`-binary compile step used in the `Dockerfile`/`docker-compose.yml` (no Node/npm involved), `regions` pins the function to `sin1` (Singapore) to stay co-located with the Neon DB region, and `git.deploymentEnabled` restricts deployments to `main`/`dev` (`"**": false` catch-all) — other branches/PRs have no working `DATABASE_URL` scoped to them, so their previews would just 500.
- **Staging**: `dev` gets its own DB (a Neon branch off the prod database, same schema, isolated data) and its own `DATABASE_URL`, set as a Vercel Preview env var scoped specifically to the `dev` branch (Vercel Hobby plan's way of doing per-branch environments — Pro adds first-class custom environments). Other preview branches (feature branches off `dev`) currently have no `DATABASE_URL` override and inherit whatever the general Preview scope is set to, if anything — deliberately not solved further until it's actually needed. `app/seed.py`'s `seed_if_empty()` populates realistic sample data into staging — run automatically by the `seed-staging` CI job after `migrate-staging`. It's per-table idempotent (checks each model's row count independently before inserting), so it's safe to re-run: already-populated tables are left alone, but a newly added model that's still empty gets seeded on the next run. The same `python -m app.seed` step also runs locally as part of `docker compose up`'s `web` command (after `alembic upgrade head`, before `uvicorn` starts) and in the `Dockerfile`'s `CMD`, so local dev gets the same sample data on a fresh DB for free. Since there's no password login to create a demo account with anymore, seeded data is **orphaned** (`user_id = NULL`) rather than owned by a fixed `demo@example.com` user — claim it after your first real OAuth login with `python -m app.manage_users assign-orphans <email>`.
- **Known gap**: SQLAlchemy's pooled `create_engine()` (`app/database.py`) isn't tuned for Vercel's short-lived serverless invocations yet — revisit (e.g. `NullPool`) if connection exhaustion becomes an actual problem; Neon's pooled connection string (used for `DATABASE_URL` everywhere) mitigates this for now. The `migrate-*` CI jobs and Vercel's deploy aren't ordered relative to each other, so a push doesn't guarantee the migration lands before/after the new code goes live.
- **`SECRET_KEY`**: needed as a real Vercel env var (Preview/`dev` and Production/`main`) once auth matters there — sessions on those deployments otherwise sign with the insecure in-code dev default. Not needed in GitHub Actions (CI never boots the actual app, only runs migrations/seed scripts against it). `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET` (`app/config.py`) are needed the same way, set to the same values in every environment (local, Preview/`dev`, Production/`main`) — one Google OAuth app and one GitHub OAuth app cover all three, each with three authorized redirect URIs registered (`http://localhost:8000/auth/<provider>/callback`, the `dev`-branch Vercel preview domain's, and the production domain's). After this feature first deploys to an environment with pre-existing data, run `poetry run python -m app.manage_users create <email>` then `assign-orphans <email>` locally (pointed at that environment's `DATABASE_URL`) to create a real account and reclaim that data — deliberately a manual, local-only step, never through CI, since this repo's Actions logs are public and any bootstrap-credential-via-migration approach would leak it.

## Versioning

`pyproject.toml`'s `[project].version` is the source of truth, following SemVer (`MAJOR.MINOR.PATCH`). The version bumps **only on the release PR from `dev` into `main`** — feature branches merging into `dev` don't touch it, so `dev` can absorb any number of merged features without implying a release happened. The `version-check` job in `.github/workflows/ci.yml` enforces this: it fails a PR targeting `main` if the version is unchanged from `main`'s current value (PRs into `dev` are exempt from this check). Bump level follows the commit-type tags already used in this repo's commit messages (see "Commit messages" above), applied to the aggregate of commits being released since the last release:
- Any `(feat)` commit since the last release → bump minor, reset patch to 0 (e.g. `1.1.0` → `1.2.0`)
- Only `(fix)`/`(chore)` commits → bump patch (e.g. `1.1.0` → `1.1.1`)
- A breaking change → bump major, reset minor/patch to 0 (e.g. `1.1.0` → `2.0.0`); call it out explicitly in the commit body since there's no dedicated marker convention yet

Pre-release, the app is versioned `0.x.y`; the first real production release is what bumps it to `1.0.0`. At release time (the `dev` → `main` PR that ships it), also tag `main` with a matching `vX.Y.Z` git tag (e.g. `v1.0.0`) — done manually, not automated.
